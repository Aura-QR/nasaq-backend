# Structured lesson preparation

The backend now creates drafts through both single and bulk preparation creation. A draft needs a lecture to establish its teacher, class and subject; all lesson content can be saved later. Existing preparations retain their fields and review statuses. No existing-row status migration is required.

## Review of the implementation plan

The shared catalogue and tenant-owned curriculum copies fit the existing tenant model. The implementation makes these adjustments:

- `pending` continues to mean submitted and awaiting review. The flow is `draft → pending → approved | needs_revision`. This preserves the existing review API and stored statuses.
- All new preparations, including uploads without a lesson and bulk uploads, start as drafts. Retaining the proposed upload-to-pending fallback would bypass the structured requirements.
- Submission requires a curriculum lesson, at least one nonblank objective, at least one valid library item and at least one resource. Supporting files satisfy none of these requirements.
- Any content, week, lecture or resource change clears the review and returns the preparation to draft. Drafts appear in the weekly screen but do not count toward submitted coverage. Review endpoints reject drafts.
- Student-view access uses the student role because existing student permissions do not grant Preparation reads. Ordinary detail/list reads also apply the same field projection and class restriction if a student has been granted those permissions. Students cannot read the weekly staff report or the curriculum suggestion catalogue.
- Teachers can create reusable library links and upload files. Existing library update/delete roles remain in force.
- Catalogue writes use a SUPER_ADMIN-only API. The seed CLI validates the source offline and writes through that API with an admin token; it does not bypass authorization through a direct database connection.
- The source path is configurable. The actual source has both three- and four-part lesson IDs. Full IDs are preserved; the first two components identify the unit, and deeper lesson names retain their existing chapter prefix. The supplied source parses as 162 subjects, 1,377 units and 8,330 lessons.

## Client flow

1. Read `GET /catalog/subjects?page=1&limit=100` and `GET /catalog/subjects/:id/units`. Units include their catalogue lessons. Reads accept authenticated school users or platform administrators.
2. An owner or manager calls `POST /curriculum/import` with `catalogSubjectId`, the school's `subjectId`, and its `gradeLevelId`.
3. Staff read `GET /curriculum/units?subjectId=...&gradeLevelId=...`, then `GET /curriculum/units/:id/lessons`. Each school lesson includes editable objective suggestions.
4. Create a draft with `POST /preparation` and `{ "lecture": "...", "lessonId": "..." }`. The lesson is optional at this stage. If supplied, its name becomes `lessonTitle`, and its objectives are copied when the request omits objectives. Sending `objectives: []` explicitly preserves the empty list.
5. Save either form step with `PATCH /preparation/:id`. Supported content fields are `lessonId`, `warmUp`, `vocabulary`, `objectives`, `digitalContentIds`, `teachingStrategies`, `strategiesOther`, `teachingAids`, `thinkingSkills`, `closure`, and `teacherInstructions`. Read pick-list defaults from `GET /preparation/reference-lists`.
6. Create library items inline through `POST /library`, then put their IDs in `digitalContentIds`. A link item uses JSON `{ "title": "...", "kind": "link", "link": "https://..." }`. A file item uses multipart fields `title`, `kind=file`, optional `subjectOfferingId`, and the binary field `file`. The library returns a reusable file reference with a `/uploads/library/...` path. File metadata is generated by the server. The upload limit is 20 MB; PDF, Office documents, images, MP3 and MP4 are supported.
7. Add a resource through `POST /preparation/:id/resources`, for example `{ "type": "homework", "title": "واجب", "description": "..." }`. Types are `homework`, `activity`, `enrichment`, and `quiz`. A quiz can use `examId`; an activity can use `projectId`. Those references must belong to the preparation's offering and class. Inline resources require a title. Optional fields are `startAt`, `dueAt`, `totalGrade`, `link`, and a validated `files` array. File entries use `filename`, `originalName`, `path`, and `size`; the resource endpoint stores references and does not upload files.
8. Call `POST /preparation/:id/submit`. It returns `data.reviewStatus = "pending"`. Empty resources return HTTP 400 with `يتعين عليك إضافة إثراء أو واجب أو اختبار أو نشاط واحد على الأقل`.

Preparation create/patch accept JSON or multipart. For multipart, send structured array fields as JSON arrays. Existing supporting uploads use the `files` field. Detail reads include `resources` and `resourcesCount`. Remove a resource with `DELETE /preparation/:id/resources/:rid`.

The existing global response interceptor may wrap these service payloads in the application's usual response envelope.

## School curriculum management

Owners and managers can create units with `POST /curriculum/units` (`subjectId`, `gradeLevelId`, `name`, `order`) and lessons with `POST /curriculum/units/:id/lessons` (`name`, `order`, optional `objectives`). Order starts at zero.

Use `PATCH /curriculum/units/:id` to rename/reorder, and `PATCH /curriculum/lessons/:id` to rename/reorder or edit objective suggestions. Delete lessons with `DELETE /curriculum/lessons/:id`; lessons referenced by preparations return 409. Delete empty units with `DELETE /curriculum/units/:id`; nonempty units return 409.

Imports are protected by unique indexes scoped to school, subject and grade. Repeated imports preserve school edits and repair missing lessons from interrupted imports. Deliberately deleting an imported lesson and importing again restores it. Later catalogue seed runs never directly rewrite a school's copy.

Submission fills empty lesson objective suggestions with a conditional update, preserving existing teacher/manager suggestions. Suggestions never cross school boundaries.

## Student reads

`GET /preparation/:id/student-view` returns only `_id`, `lessonId`, `lessonTitle`, `warmUp`, `vocabulary`, `objectives`, `digitalContentIds`, `thinkingSkills`, `closure`, and `teacherInstructions`. References remain IDs. It does not embed internal strategy fields, review notes, lesson suggestions or exam answers.

Students see pending/approved preparations for their active enrolled classes. Legacy students with no enrollment records use their stored class. Drafts, needs-revision records and other classes are hidden. Teacher reads of this endpoint are limited to the teacher's own preparations.

## Seeding and verification

Dry run (the default; no database or API writes):

```powershell
npm run seed:catalog -- --source 'D:\Work\Aura\7ader\subjects_and_lessons.json'
```

For an authorized platform seed, set `CATALOG_API_URL` to the backend base URL and `CATALOG_ADMIN_TOKEN` to a SUPER_ADMIN token, then use:

```powershell
npm run seed:catalog -- --source 'D:\Work\Aura\7ader\subjects_and_lessons.json' --apply
```

`CATALOG_SOURCE` can replace `--source`. `--dry-run` always disables writes, even alongside `--apply`. The script upserts by source ID and is safe to rerun after interruption. Remote seeding requires HTTPS.

```powershell
npm run build
npm test -- --runInBand
```

The structured integration suite uses the separate `nasaq-structured-test` database and covers HTTP authorization, draft submission, tenant isolation, concurrent imports/submits, student projection, legacy reads, resource validation, and library uploads. Existing suites must continue to run serially because they share a database.

Verified locally: production build passed; all 25 suites and 418 tests passed with `--runInBand`. Catalogue seeding was verified in dry-run mode only; the platform catalogue still needs an authorized `--apply` run against the target backend.
